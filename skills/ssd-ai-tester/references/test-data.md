# ข้อมูลทดสอบและการรันซ้ำ

อ่านก่อนเตรียมข้อมูล สร้างสคริปต์ หรือทำ action กับระบบจริง ใช้ร่วมกับ [playwright.md](playwright.md) หรือ [browser-use.md](browser-use.md) ตามวิธีรัน ไม่ต้องสร้างข้อมูลใหม่เมื่อเคสใช้ข้อมูลเดิมได้อย่างถูกต้อง

## เลือกข้อมูลจากบริบท

หา requirement/AC, fixtures, test-data และ config เดิมก่อนสร้างใหม่ ตรวจบทบาท เจ้าของข้อมูล สถานะรายการ และ environment ให้ตรงเคส ใช้ source อธิบายรูปแบบ/validation แต่ไม่ใช้ค่าจาก implementation แทนเกณฑ์ธุรกิจที่ยังไม่ยืนยัน

แยกประเภทข้อมูลของแต่ละเคส:

- อ่านอย่างเดียว: ใช้รายการที่มีอยู่และสิทธิ์เหมาะสม ตรวจว่ายังตรง precondition
- สร้าง/แก้รายการ: ใช้ข้อมูลทดสอบที่ได้รับอนุญาต กำหนดชื่อหรือ reference เฉพาะรอบ และเก็บ ID ที่ระบบสร้างเมื่อสังเกตได้
- Negative/boundary: สร้างค่าที่ผิดเฉพาะเงื่อนไขที่ตั้งใจตรวจ เช่น เกินวงเงิน โดยเงื่อนไขอื่นต้องพร้อม ระบุค่าขอบเขตจาก AC หรือทำเครื่องหมายว่าเป็นข้อสันนิษฐาน

อย่าใช้ค่าจำลองใน field ทุกชนิดโดยไม่ตรวจระบบ เช่น เบอร์หรือ email ที่ดูเป็นของทดสอบอาจส่งข้อความถึงบุคคลจริง ต้องใช้ sandbox/บัญชี/ปลายทางทดสอบที่มีอยู่และได้รับอนุญาต หากเตรียมไม่ได้ให้ blocked เฉพาะเคส ไม่เปลี่ยนไปใช้ข้อมูลจริงเอง

## เก็บไฟล์และข้อมูลเฉพาะเครื่อง

เก็บข้อมูลทั่วไปที่ไม่ลับใน test-data/ ของ workspace; ใช้ไฟล์ local/config ที่โปรเจกต์รองรับจริงสำหรับค่าเฉพาะเครื่องและตรวจ gitignore ก่อน commit ไม่สมมติว่าทุก workspace รองรับ scenario.local.json เหมือนตัวอย่าง Telesale

เก็บ auth/session ใน playwright/.auth/ ตาม config ที่รองรับ ห้ามใส่ password, OTP, token หรือ session ใน source, plan, report หรือภาพส่งมอบ ระวัง trace/network log และเอกสารแนบเช่นเดียวกัน ไม่คัดลอก production database หรือทำข้อมูลจำลองจากข้อมูลจริงโดยไม่มีขอบเขตอนุญาต

## ป้องกันรายการซ้ำ

1. ก่อนส่ง action ที่เขียนข้อมูล ตรวจว่าเป็นรอบใหม่หรือการทำต่อจากรอบที่ล้มเหลว ค้นผลเดิมจาก run log/ID และ UI ที่อนุญาต ไม่สั่ง create ใหม่เพียงเพราะสคริปต์ timeout
2. ใช้ reference เฉพาะรอบที่ผ่าน validation และไม่เก็บข้อมูลส่วนบุคคล เช่น prefix ทดสอบร่วมกับ run ID; ไม่ถือว่าชื่อไม่ซ้ำรับประกัน idempotency
3. หลังส่ง ตรวจผลยืนยันและ ID/สถานะที่ผู้ใช้เห็น แล้วจดว่ารอบนี้สร้างหรือแก้รายการใด ไม่สรุปว่าไม่เกิดรายการเพียงเพราะไม่เห็น success message
4. ถ้าไม่ทราบว่ารายการถูกสร้างแล้วหรือไม่ และตรวจไม่ได้ ให้ blocked พร้อมเหตุผล ห้ามกดส่งซ้ำหรือเปิด retry อัตโนมัติ

นำข้อมูลเดิมกลับมาใช้เมื่อเคสอนุญาตและสถานะถูกต้อง เคสที่ทดสอบ duplicate ต้องใช้ค่าซ้ำอย่างตั้งใจและตรวจ expected จาก AC

## หลังรัน

บันทึกข้อมูลอ้างอิงที่ไม่ลับและผลข้างเคียงในผลรอบนั้นตาม [results-format.md](results-format.md) ระบุว่าข้อมูลยังอยู่หรือ cleanup แล้ว ลบ/ย้อนสถานะได้เฉพาะที่ขอบเขตงานอนุญาตและยืนยันเป้าหมายชัดเจน ไม่ทำ cleanup อัตโนมัติกับข้อมูลใช้ร่วมกัน

การรันแบบ worker เดียวและไม่ retry ช่วยลดความเสี่ยง แต่ไม่รับประกันว่า action จะไม่ซ้ำ ต้องตรวจผลรอบก่อนตามขั้นตอนนี้ด้วย
