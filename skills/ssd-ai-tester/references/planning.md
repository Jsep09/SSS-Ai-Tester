# การออกแบบแผนทดสอบ

เริ่มจากงานที่ผู้ใช้ต้องทำสำเร็จและเงื่อนไขยอมรับที่มีแหล่งอ้างอิง ไม่เริ่มจากชื่อ component หรือ API

สำหรับ smoke ให้เลือกเส้นทางสำคัญตามระบบ เช่น เข้าหน้าหลัก ค้นหารายการ เปิดรายละเอียด กรอกข้อมูล บันทึกแล้วพบรายการ สำหรับ regression เลือกงานที่เปลี่ยนและเส้นทางข้างเคียง ไม่ต้องกำหนดจำนวนกรณีตายตัว

เพิ่มกรณีข้อมูลถูกต้อง ข้อมูลบังคับว่าง รูปแบบไม่ถูกต้อง ขอบเขตค่า และการย้อนกลับ/โหลดใหม่เมื่อเกี่ยวข้องกับ requirement ตรวจบทบาทหรือหน้าจอขนาดต่าง ๆ เฉพาะเมื่ออยู่ในขอบเขตและมีวิธีทำได้จริง

แผน `test-plan.md` ต้องมี:

- ระบบ / URL / สภาพแวดล้อม / บทบาท / ขอบเขตที่ตรวจและไม่ตรวจ
- แหล่งเงื่อนไขธุรกิจ และสมมติฐานที่รอยืนยัน
- ข้อมูลเตรียมทดสอบที่ไม่ใช่ความลับ
- ตารางกรณี: รหัส, เงื่อนไขธุรกิจ, ชื่องาน, ความสำคัญ, สิ่งที่ต้องพร้อม, ขั้นตอน, ผลที่คาดหวัง
- จุดที่ต้องเก็บภาพและข้อจำกัด เช่น session หมดอายุหรือไม่มีสิทธิ์

ใช้ชื่อ “ค้นหาเลขคำขอแล้วพบรายการตรงกัน” แทน “test search endpoint” ขั้นตอนใช้ชื่อปุ่ม/ช่องที่ BA/QA อ่านแล้วทำตามได้

แผนเป็นสิ่งที่จะทดสอบ ไม่ใช่ผลทดสอบ แผนที่ยังไม่ได้รันต้องไม่มีตราผ่านหรือภาพสาธิตที่อ้างเป็นหลักฐานจริง
