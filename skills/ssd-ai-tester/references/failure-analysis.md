# วิเคราะห์ก่อนแก้หรือรันซ้ำ

เมื่อ assertion ล้มเหลว โหลดสคริปต์ไม่ได้ login ไม่สำเร็จ หรือผลยังสรุปไม่ได้ อ่านผลของรอบเดิมก่อน ห้ามเริ่มด้วยการเพิ่ม timeout/retry หรือแก้ expected เพื่อให้ผ่าน

## เก็บหลักฐานแล้วแยกสาเหตุ

1. ระบุเคส ขั้นตอน และ error แรกที่ทำให้ flow ไปต่อไม่ได้ อ่าน runner.log, technical-results.json, report.json และภาพ/trace ที่มี ไม่ถือว่าข้อผิดพลาดต่อเนื่องทุกอันเป็นคนละบั๊ก
2. ตรวจ URL/environment, context hash/review และ revision ของ deployment เท่าที่ทราบ โค้ดต่างเวอร์ชันเป็นข้อจำกัดก่อนสรุปว่า locator หรือระบบผิด
3. ตรวจ AC, precondition และข้อมูลของเคสนั้น แยกสิ่งที่สังเกตจริงออกจากข้อสันนิษฐาน

| สาเหตุ | หลักฐานที่ควรตรวจ | วิธีดำเนินการ |
| --- | --- | --- |
| Script | syntax/import error, selector ไม่ตรง DOM/source ปัจจุบัน, ขั้นตอนสคริปต์ผิดจาก flow | แก้เฉพาะจุดที่มีหลักฐาน ตรวจว่าหน้าระบบเปลี่ยนผิด AC หรือไม่ก่อนถือว่าเป็น script แล้วรันเคสที่กระทบ |
| Application | ข้อมูล/สิทธิ์พร้อม และผลจริงขัดกับ AC ที่ยืนยันแล้ว | เก็บขั้นตอน ผลคาดหวัง/ผลจริงและหลักฐาน รายงาน failed ไม่แก้ test เพื่อยอมรับผลผิด |
| Data | ข้อมูลไม่พบ ถูกใช้แล้ว ซ้ำ อยู่ผิดสถานะ หรือ precondition ไม่ครบ | อ่าน [test-data.md](test-data.md); เตรียมข้อมูลที่อนุญาตหรือรายงาน blocked ไม่ตีเป็น application bug โดยอัตโนมัติ |
| Auth/Permission | session หมดอายุ, redirect login, 401/403, role ไม่ตรง | ตรวจบทบาทที่เคสกำหนด ให้ผู้ใช้ login เองตาม runtime; กรณีทดสอบห้ามเข้าถึงโดยตั้งใจอาจเป็น passed หากตรง AC |
| Environment/Runtime | browser/runtime ไม่พร้อม, DNS/TLS/network, ระบบเป้าหมายเข้าไม่ได้ | แก้ความพร้อมภายในขอบเขตหรือ blocked ไม่เปลี่ยนไปยิง backend แล้วอ้างว่า UI ผ่าน |
| ยังสรุปไม่ได้ | หลักฐานไม่พอหรือแยกได้หลายสาเหตุ | ระบุสิ่งที่ทราบและข้อมูลที่ต้องหา ใช้ blocked แทนการยืนยันบั๊ก |

HTTP error หรือ timeout อย่างเดียวไม่พิสูจน์ root cause เช่น locator timeout อาจเกิดจากหน้าล่ม สิทธิ์ผิด หรือ script ผิด สำรวจ Browser Use เฉพาะจุดที่ภาพ/trace/source ตอบไม่ได้ ไม่สำรวจ flow เดิมทั้งหมดซ้ำ

## เงื่อนไขรันซ้ำ

- อ่าน [test-data.md](test-data.md) ก่อนรัน flow ที่เขียนข้อมูล ตรวจสถานะรายการรอบก่อนด้วย UI ก่อนส่งซ้ำ หากไม่ทราบว่าสำเร็จหรือไม่ ให้หยุดเฉพาะเคสนั้นและระบุ blocked
- รันเฉพาะเคสที่เกี่ยวข้องหลังแก้สาเหตุหรือมีหลักฐานใหม่ ไม่เปิด retries เพิ่มเพื่อกลบความไม่แน่นอน ถ้าล้มเหลวสาเหตุเดิมและไม่มีสิ่งที่แก้ได้เพิ่ม ให้สรุปอุปสรรคแทนการวนซ้ำ
- เก็บผลและหลักฐานแต่ละรอบแยกกัน เชื่อมรอบใหม่กับรอบที่ล้มเหลว ไม่เขียนทับหรือลบรอบก่อนเพื่อทำให้รายงานดูผ่าน
- ถ้า context เปลี่ยนระหว่างวิเคราะห์ ให้ทำ [code-context.md](code-context.md) ใหม่ก่อน run; การแก้ locator ไม่ยกเว้น context gate

## ส่งผลให้ตรวจต่อได้

ใช้ schema/status จาก [results-format.md](results-format.md) เดิม ประเภทสาเหตุข้างต้นไม่ใช่ status ใหม่ หากต้องอธิบายเพิ่มใช้ reason/actual หรือบันทึก failure-analysis.md ในโฟลเดอร์รอบนั้น อ้างเคสและไฟล์หลักฐาน พร้อมสาเหตุที่ยืนยันแล้วหรือสมมติฐาน สิ่งที่แก้ และสิ่งที่ต้องทำต่อ

รายงานอัตโนมัติอาจระบุ assertion failure ก่อน AI วิเคราะห์ ต้องอ่านหลักฐานก่อนสรุปเป็นบั๊กธุรกิจ ถ้าเกณฑ์ไม่ชัดหรือเป็นปัญหา precondition ให้คงผลเทคนิคเดิมและอธิบายข้อจำกัดในการสรุปธุรกิจ
