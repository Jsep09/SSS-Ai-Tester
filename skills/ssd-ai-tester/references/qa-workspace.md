# มาตรฐาน Workspace ของ BA/QA หลังติดตั้ง

นี่คือพื้นที่ทำงานของผู้ใช้ ไม่ใช่โครง Repo สำหรับพัฒนา/ติดตั้ง SSD AI Tester ไม่ย้าย bin/, lib/, skills/, test/, dist/ หรือ runtime ของชุดติดตั้งตามมาตรฐานนี้ และไม่สร้างงานทดสอบในโฟลเดอร์ติดตั้ง Skill

## เริ่มต้นครั้งแรก

เมื่อผู้ใช้เริ่มใช้ `$ssd-get-started` หรือ `$ssd-ai-tester` เพื่อเริ่มงานครั้งแรก ให้ AI สร้างโครง Workspace จริงในพื้นที่ที่เขียนได้ ไม่จบที่แสดงต้นไม้หรือเสนอว่าจะสร้างให้ ไม่สร้างซ้ำเมื่อมีระบบนั้นอยู่แล้ว ไม่ใช้ขั้นตอนนี้กับงานแสดงรายการ Skill/ตรวจรุ่น/report-only หรือทางลัดรันสคริปต์เดิม

1. ใช้ Root และชื่อระบบจากคำขอ/พื้นที่งานปัจจุบัน Root เป็นโฟลเดอร์ใดก็ได้ ผู้ใช้เปลี่ยนชื่อระบบได้ ถ้ายังไม่มีระบบจริง ใช้ **Telesale** เป็นตัวอย่าง หากพื้นที่ปัจจุบันเป็น Repo พัฒนา/โฟลเดอร์ติดตั้ง ให้เลือกพื้นที่งานแยกที่ได้รับอนุญาต เช่น `<พื้นที่ผู้ใช้>/QA-workspace` ไม่ hardcode ชื่อผู้ใช้หรือ Desktop ของเครื่องนี้ ถ้าไม่มีพื้นที่ที่เขียนได้จริงจึงถามหา Root
2. ตรวจระบบเดิมก่อน ถ้ามีอยู่แล้วให้อ่านและใช้ต่อ ไม่เขียนทับ ไม่จัดย้ายเอง ถ้ายังไม่มี เรียก helper จากชุดติดตั้ง:

   ```text
   node "<skill>/scripts/scaffold-workspace.mjs" --root "<Root>" --system "Telesale"
   ```

   ใส่ `--url` และ `--environment` เมื่อทราบจริง ไม่ต้องรอ URL เพื่อสร้างโครงเปล่า helper ไม่ติดตั้ง runtime ไม่เปิดเว็บ และไม่รันทดสอบ
3. แจ้งตำแหน่งจริงและชี้ `อ่านก่อน.txt`, `input/`, `codebase/`, `run/`, `results/` ให้ผู้ใช้ บอกว่าเป็นโครงเริ่มต้น ยังไม่มี Flow พร้อมรันหรือผลทดสอบ
4. เมื่อมี requirement/URL/ข้อมูลเพียงพอ จึงเตรียม Flow จริงตามขอบเขต สร้างตัวเรียกเมื่อเชื่อมสคริปต์ได้จริง ไม่สร้าง `.cmd` หลอกที่ไม่รันอะไร ไม่สร้างผลล่าสุด/ประวัติปลอม หากผู้ใช้สั่งเตรียมหรือทดสอบต่อแล้ว ให้ทำต่อโดยไม่บังคับกลับมาเรียก Skill อีกรอบ

## โครงสร้างต่อหนึ่งระบบ

```text
<Root>/
└── <ชื่อระบบ>/                  เช่น Telesale หรือ Claimmotor
    ├── อ่านก่อน.txt
    ├── input/
    ├── codebase/
    ├── scripts/
    │   └── <ชื่อ Flow>/
    ├── run/
    │   └── <ชื่อ Flow>.cmd
    ├── results/
    │   └── <ชื่อ Flow>/
    │       ├── ล่าสุด.html
    │       └── history/
    └── .system/
```

ตอนเริ่มต้นสร้างเพียงโฟลเดอร์หลักและ `อ่านก่อน.txt` โฟลเดอร์ Flow, ตัวเรียก และผลลัพธ์เพิ่มเมื่อมีงานจริง ไม่เติมไฟล์ตัวอย่างโดยไม่จำเป็น

- `อ่านก่อน.txt`: ระบบ สภาพแวดล้อม URL จุดสั่งรัน จุดดูผล และผลข้างเคียงของ Flow ถ้ายังไม่ทราบให้เขียนว่ายังไม่ระบุ อัปเดตเมื่อเตรียม Flow จริง
- `input/`: requirement, AC และข้อมูลทดสอบที่ใช้จริง ไม่สร้างโฟลเดอร์ย่อยหรือ fixture ที่ไม่จำเป็น
- `codebase/`: source/Repomix XML ของหน้าบ้านและหลังบ้าน เช่น `frontend.xml`, `backend.xml` เป็นเพียงตัวอย่างชื่อ ใช้ชื่อไฟล์จริงได้ ไม่สร้าง XML เปล่า ไม่บังคับให้มีครบทั้งสองฝั่ง ไม่คัดลอก bundle เดียวกันซ้ำใน input/ ให้อ้างอิงจากที่เดียว
- `scripts/<Flow>/`: สคริปต์และตัวช่วยของ Flow ใช้ร่วมกันระหว่างโหมดดูบอตกับโหมดเร็ว ถ้ากรณีต่างกันจริงจึงแยกสคริปต์ ตัวช่วยร่วมหลาย Flow วางใน scripts/ ตามที่ใช้งานจริง
- `run/<Flow>.cmd`: จุดหลักของ BA/QA หนึ่งไฟล์ต่อ Flow รัน process โดยตรงโดยไม่ต้องมี AI เลือกโหมดผ่าน argument หรือเมนูในไฟล์เดียว แสดงระบบ environment และการสร้าง/แก้ไขข้อมูลก่อนรัน
- `results/<Flow>/history/<รหัสรอบ>/`: ผลและหลักฐานของแต่ละรอบจริง ไม่เขียนทับประวัติ `ล่าสุด.html` ต้องบอกเวลา สภาพแวดล้อม สถานะและรหัสรอบ หากทำรายงานเต็มให้เป็น HTML ที่ส่งต่อได้ตาม results-format.md ถ้า quick ยังไม่ได้สร้าง HTML ให้แจ้งตรง ๆ และชี้ summary.json ของรอบใหม่ ห้ามแสดงผลเก่าว่าเป็นรอบล่าสุดหรือรันซ้ำเพื่อเปิดผล
- `.system/`: config, session/auth, cache, locks, context manifest/review/code-map และตัวเชื่อม runner ข้อมูลภายในไม่ปะปนในจุดใช้งาน BA/QA ไม่ commit/share credential หรือ session

ตัวอย่างการอธิบาย Telesale: “วาง requirement/ข้อมูลใน Telesale/input และ XML หน้าบ้านหลังบ้านใน Telesale/codebase เมื่อเตรียม Flow ค้นหาคำขอเสร็จ ใช้ run/ค้นหาคำขอ.cmd ดูผลที่ results/ค้นหาคำขอ/ล่าสุด.html” นี่เป็นตัวอย่างเส้นทาง ไม่ใช่หลักฐานว่ามี Flow นั้นแล้ว ห้ามคัดลอก Flow สร้างใบคำขอจาก examples/telesale แล้วรันทันทีโดยไม่มีขอบเขต/ข้อมูล/สิทธิ์ของงานนั้น

## เส้นทางและ runtime

- ตัวเรียกหาตำแหน่งระบบจาก `%~dp0` ของตนเอง เช่น `for %%I in ("%~dp0..") do set "QA_SYSTEM_ROOT=%%~fI"` quote path ทุกจุด ไม่พึ่ง working directory และไม่ฝังชื่อผู้ใช้ Root หรือชื่อระบบ
- เก็บ path ของ input/codebase/scripts/results เป็น relative ต่อระบบ แปลงเป็น absolute ตอนเรียกคำสั่งที่ต้องการเท่านั้น เมื่อย้าย Root/เปลี่ยนชื่อระบบ ตรวจ context path และ hash ใหม่ ไม่อ้างว่า context เดิมใช้ได้โดยไม่ตรวจ
- หา Skill/runtime จากกลไกติดตั้งหรือ config ที่ชุดรองรับ ไม่ฝัง path เครื่องพัฒนา ไม่คัดลอก runtime ทุก Flow ถ้า runtime หาไม่พบให้บอกวิธีตั้งค่าจริง ไม่เรียก npm install แบบไม่ pin เอง
- ตรวจด้วยชื่อภาษาไทย/ช่องว่าง เรียกจาก working directory อื่น ย้าย Root และเปลี่ยนชื่อระบบ ตรวจทั้ง import/config/context/ตัวเรียก/รายงาน ห้ามถือว่าการย้ายโฟลเดอร์อย่างเดียวเสร็จแล้ว

## ขอบเขต helper รุ่นปัจจุบัน

`scaffold-workspace.mjs` สร้างโครง BA/QA เท่านั้น ส่วน `workspace.mjs workspace` และ `bind` เป็น helper แบบเดิมที่ยังสร้าง ssd-workspace.json, tests/, runs/, .ssd/ และตัวเชื่อมที่ผูกตำแหน่งติดตั้ง ไม่ใช้สองคำสั่งนี้ที่ root ของระบบใหม่แล้วอ้างว่าตรงมาตรฐานนี้ และไม่กล่าวว่า scaffold พร้อมรัน Playwright แล้ว

การเตรียม Flow ต้องจัดตัวเชื่อม/config และตรวจการทำงานจริงให้รองรับโครงนี้ก่อนส่งมอบ หาก runner ที่มีอยู่ยังรองรับไม่ได้ ให้รายงานข้อจำกัดอย่างชัดเจน ห้ามซ่อน workspace เก่าทั้งชุดไว้ต่อ Flow หรือข้าม context/evidence gate เพื่อทำให้ดูเหมือนพร้อม โครงเก่าใน playwright.md/code-context.md ใช้อธิบาย helper เดิมสำหรับดูแลงานเดิม ไม่เปลี่ยนมาตรฐานงานใหม่

มาตรฐานนี้ใช้กับงานใหม่ การย้ายระบบเดิมต้องเป็นขอบเขตที่ผู้ใช้สั่ง ไม่จัดย้าย Telesale, Claimmotor หรือระบบอื่นเองจากการเริ่มใช้ Skill
